PARAKIT / PRODUCT DESIGN & DEVELOPMENT

Designing closer to the real product

I designed and built a VS Code fork to help Autodesk designers get started in their team’s repository, work more efficiently and spend less time on setup and Git.

My role
Product design & development
Collaboration

Designers at Autodesk

The opportunity and the problem

Designers should focus on design

01 / The old way

A replica is never the real experience

Figma prototypes and replicas require extra work to recreate existing behavior, while details and ongoing changes get missed.

02 / The opportunity

Working in code can save design time

Use the real product, build with engineers and automate recurring work to make designers more efficient.

03 / The barrier

Engineering work pulls focus from design

Git, local environments and terminals add friction before designers can explore and refine the experience.

Two designer personas

Comfortable with code

Enjoys code and the terminal. Wants to spend less time on setup and more time exploring ideas.

Unsure of the workflow

Finds Git and terminal commands confusing. Needs familiar actions and clarity about where changes go.

Branch protection

Balancing autosave and branch protection

Supports01 Open ↗02 Start ↗03 Edit & save ↗

Designers need to experiment and have their work saved automatically. Engineers need shared branches kept clear of unreviewed design changes.

I made design branches the place for exploration, with automatic commits and pushes. On other branches, Parakit keeps edits local and offers a way to move them into a design branch.

Visual editing

Editing what you see

Supports03 Edit & check ↗

Selection connects a request to an element in the running app. Designers can adjust properties, move elements or ask Claude for a change.

Edits are staged so the designer can inspect and undo them. Sending them to Claude applies the changes to the source.

Previewing different states

The Variants menu makes loading, empty, error and role-specific states available in the preview, once Claude has set them up.

Reusable workflows

Finding the right skill

Supports03 Review the work ↗04 Hand off ↗

I made common skills visible beside the AI assistant, including reviewing flows, checking edge cases and generating specs.

Each action prepares a prompt for review. Ready-made skills give designers a starting point, and they can add their own.

I designed and built the experience, with engineering help on technical work. The recordings show it running on the Lumen demo project.

Reflection

What I learned

A better tool still asks people to change

People can be hesitant to replace tools and workflows they use every day. A more efficient approach on its own isn’t always enough to make that change worthwhile.

Onboarding is part of the experience

When getting a repository running had friction, even with Parakit helping, I saw how quickly frustration could stop people from getting started. The path to the first working preview matters as much as the work that follows.

Know the limits of my technical understanding

Building with AI let me take on more, but it didn’t remove the limits of what I understand. Even with the latest models, there are things I can’t yet build correctly on my own. I need to be cautious, humble and involve engineering expertise where it matters.
